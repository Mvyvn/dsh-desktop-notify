# 串口 LED 状态灯协议

> 本插件的一条独立能力线（默认关闭，不影响通知行为）。
> 它描述三件事：真机（AI Status Lights）的**帧格式**、主机端的**渲染与背压**、以及其它插件
> 通过 `ctx.get('desktopNotify').led` 能用的**对外 API**。

## 0. 硬件与它解决什么

人躺床上时看不到屏幕：AI 是不是还在跑、是不是在等你回话、是不是已经做完了、
是不是出错了 —— 这些原本只能靠系统通知（弹一下就没了）。这块板子把状态变成
**一直亮着的颜色**。

硬件是 **[AI Status Lights](https://github.com/Mvyvn/AI_Status_Lights)**（同作者的另一个仓库）：

| 项 | 值 |
| --- | --- |
| MCU | CH32V003F4P6（RV32EC，16 KB Flash / 2 KB RAM） |
| 灯 | **7 颗 WS2812B** 串联（索引 0 = 最靠近 MCU 那颗） |
| 蜂鸣器 | 无源，频率 + 音量 + 时长 |
| 串口 | USART1，**固定 115200 8-N-1**（不可配） |

固件只有三条命令 —— **没有本地方案、没有亮度命令、没有动画**。所以：

- **颜色归固件**（设 7 颗灯的 RGB，立即刷新）；
- **动画/亮度/提醒节奏归主机**（`src/led-render.ts` 按时刻算像素，目标 240fps 推流）；
- 改个动画不用重烧固件，代价是主机卡顿时灯会顿一下。

## 0. 数据来源审计（不重复造轮子）

指示灯这一半**只做两件事**：把"状态"翻译成"画面"、把画面写进串口。
状态本身一律取自 DSH 或插件主程序已有的接口/事件，不自建探测：

| 需要的信息 | 来源 | 归属 |
| --- | --- | --- |
| 哪些会话存在 | `ctx.get('agents').roots()` / `list()` | DSH 接口 |
| agent 在不在跑 | `agent/status` 事件（+ `agent.status` 快照纠偏） | DSH 事件 |
| 回合开着没有 | `sessionProjections.stateOf(session,'turnBoundary')` | DSH 接口 |
| 待处理输入 | `stateOf(session,'inbox')` | DSH 接口 |
| **是否在等你回答** | ① `stateOf(...,'userQuestions')`（**只收录带 timeout 的提问**）② 主程序 `tools/execute` 钩子配对（阻塞式提问） | DSH + 主程序 |
| 悬置审批 | 主程序 `approval/asked`+`decided` 配对 | 主程序 |
| 后台任务 | `ctx.get('jobs').list(sessionId)`；`jobs settled` 事件 | DSH 接口/事件 |
| 子代理 | `subagent/end` 事件 + 会话血缘 | DSH 事件 |
| 目标阶段 | `ctx.get('goals').get(agent).phase` | DSH 接口 |
| **是否干过活（完成 vs 空闲）** | `session/event` 的 `turn/start`、`tool/call` 溯源 | **主程序事件** |
| 人是否在看页面 | `pages.focusedLive()`（与通知门控同一份真相） | 主程序门控 |
| 设备在不在 | 串口枚举（worker 里读注册表，按需 + 15s 兜底） | 我们（Win32 无事件接口） |

### 不做的事（避免重复实现）

* 不自建"通知去重/静音"——沿用主程序的 `notify()` 与门控；
* 不自建"任务完成判定"的另一套事件订阅——直接复用 `session/event` 那条流；
* 不用"时间窗口/采样命中"去猜状态（曾用 600ms 稳定窗口与采样式 sawWork，均已删除）。

### 轮询收敛

| 轮询 | 频率 | 为什么还需要 |
| --- | --- | --- |
| 事实采样 | **1.5s**（纠偏）+ 事件 nudge（去抖 ≤10/s） | 防漏事件；状态驱动实际来自事件 |
| 串口探测 | 2.5s | 这是**断线检测的事件源**（板子不会主动告知） |
| 端口枚举 | 断开时 15s / **auto 多灯时每 15s 重扫**挂新灯 / 页面轮询状态时按需（节流 1s） | Win32 没有设备热插拔回调，只能枚举 |
| 串口读取泵 | 等回包窗口 **2ms** / 其余 **30ms** | 只有握手/探测时才有回包；动画帧走写路径，不依赖读 |

## 1. 帧格式（与固件 `User/protocol.c` 逐字节一致）

```
+------+------+------+------------------+----------+------+
| 0x55 | 0xAA | MODE | PAYLOAD (0..21B) | CHECKSUM | 0xBB |
+------+------+------+------------------+----------+------+
  帧头   帧头   命令        数据             校验     帧尾
```

**校验和**：从帧头 `0x55` 开始累加，一直到 payload 最后一个字节，取低 8 位（不含帧尾）：

```python
checksum = (0x55 + 0xAA + MODE + sum(payload)) & 0xFF
```

| MODE | 功能 | PAYLOAD | 整帧 | 设备动作 |
| --- | --- | --- | --- | --- |
| `0x00` | 验证握手 | 无 | **5 B** | 回 ASCII `AI Status Lights OK\r\n`（21 B） |
| `0x01` | 设 7 颗灯颜色 | 21 B（7×RGB） | **26 B** | 立即刷新 |
| `0x02` | 蜂鸣 | 5 B（频率 u16LE / 音量 u8 / 时长 u16LE） | **10 B** | 非阻塞响一声 |
| 其它 | — | — | — | 整帧丢弃并重新同步 |

编码实现：`src/led-protocol.ts`（`encodeVerify` / `encodeLeds` / `encodeBuzzer`）。
测试直接用 AI_Status_Lights README 里的示例帧做向量，逐字节比对（`tests/led-protocol.test.mjs`）。

### 握手

打开串口后先发 `55 AA 00 FF BB`，**收到那行 ASCII 才算连上**。为什么要握手：
一台机器上往往还插着手机/下载器之类的 COM 口，"打开成功"不代表它是本板子。
握手超时（默认 1.5s）会关掉端口、按退避重连，并在设置页显示「异常」。

### 设备发现：多灯**同时驱动**（auto）/ 手动端口（可多块，英文逗号分隔）

参考上位机是"列出所有串口 → 逐个发验证帧 → 谁应答谁就是板子"。本插件也这么发现，但
**不再只保留第一个应答的**：多块灯插在同一台机器上时，`auto` 会把每一块都挂上，同时推同一份画面。

| 步骤 | 行为 |
| --- | --- |
| 候选排序 | USB 转串口（CH34x / VCP / USBSER / 描述里带 "USB-SERIAL"）优先，其次 COM 号从大到小；**谁是真板子仍由握手回答** |
| 并行探测 | 每个候选各建一条**固定端口**的子链路，各自 1.5s 握手窗口，互不排队 |
| 应答 | 保留，持续接收广播帧（同一帧内容、各自独立队列/worker） |
| 不应答 / 打不开 | 关闭该子链路并冷却 **30s**，不反复砸同一个口 |
| 周期重扫 | 每 **15s** 重新枚举一次：新插入的灯自动挂上；已握手但拔掉的灯由子链路自己退避重连（故障隔离） |
| 手动端口 | `COM5` 只驱动一块；`COM5,COM9`（**英文逗号**）驱动列出的多块；不枚举、不发现 |
| 写了 `auto` | 例如 `auto,COM5` → **整体按 auto**（auto 已包含所有灯，其余项直接忽略） |

多灯同步的几个事实：

* **画面一致、传输独立**：每帧内容由主机时钟算好，广播给所有子链路；各自的 worker / 有界队列 /
  重连互不影响 —— 一块掉线不会拖慢另一块（一块的 `fail()` 只熄自己）。
* **带宽**：每条串口各占 54.2%，**不是共享**；N 块灯 = N 条 115200。
* **关灯/退出**：`flush()` / `close()` 广播到所有板子（每块都收到全黑帧再关句柄）。
* **代价**：N 块 = N 份渲染/编码（240fps 下 2~5 块可忽略；更多时应共享一帧编码，见"长期方向"）。

### 线程边界（灯的阻塞不会影响主插件）

灯的全部时间驱动逻辑跑在**独立 worker 线程**（`src/led-runtime-worker.ts`）：

| 线程 | 做什么 |
| --- | --- |
| 主线程 | 采样本机的 agent/jobs/投影（只能用主线程的 ctx API）→ 判定 → **只下发语义画面**（签名去重，不会每拍 postMessage）；`status()` 读缓存快照 |
| 灯运行时 worker | 240fps 帧循环、渲染/交叉渐变、自检动画、熄灯淡出、蜂鸣排队、串口链路管理（再往下才是 native 串口 worker） |
| 串口 worker | koffi/Win32 串口原生调用（卡死时被看门狗 terminate，只死它自己） |

因此主线程的事件循环卡顿/GC 不会让灯掉帧；灯侧任何阻塞/崩溃也只影响灯 worker（bridge 5s 退避
自动重启）。排障时可用 `DSH_LED_RUNTIME=inline` 强制回到主线程内联运行时做对照；退出路径是唯一
允许主线程同步等待的地方（发 shutdown，最多 1200ms 等全黑帧落地）。

边界：Windows 侧枚举只拿得到 COM 号 + 设备接口名（注册表 `SERIALCOMM`），**没有 VID/PID**，
所以"CH340 优先"只能靠名称匹配；真正可靠的身份判定始终是握手回包。

### 容错

- 未知 MODE / 校验错 / 帧尾不对：固件整帧丢弃，不影响后续帧；
- `55 55 AA` 也能正确重同步；
- 帧内字节间隔 >20ms 视为半截帧丢弃（固件的看门狗）；
- 主机侧：像素没变就不写（稳态 0 B/s），每 **1s** 心跳重发一次防丢帧（`HEARTBEAT_MS`）。

### 链路自愈与自适应冗余（不改固件能做到的极限）

**先说边界**：固件只认 0x00 验证 / 0x01 设色 / 0x02 蜂鸣；颜色 payload **定长 21B**，
既没有逐帧 ACK/CRC 回执，也没有压缩/增量的余地。所以不改固件**做不到**"逐帧校验 + 补发
丢失的那一帧"，也做不到线缆级压缩。能利用的是：**每帧都是绝对状态**（丢帧不会留下错色，
下一帧自动纠正）与**空闲带宽**（健康时只占 54.2%）。

| 机制 | 触发 | 行为 | 代价 |
| --- | --- | --- | --- |
| 状态自愈 | 任何丢帧/坏帧 | 不推进"已发送快照"→ 下一拍用最新画面重发；重连后当前画面立即落地 | 无 |
| 自适应双发 | 10s 窗口内持续丢帧/写失败/探测超时/重连（单帧偶发丢不算） | 唯一帧降到 120fps，每帧**连写两份**（第二份必达；`pending===0` 才补） | 线上占用仍 ≈54.2%，不额外带宽 |
| 快速健康探针 | 冗余期 | 0x00 验证帧 2500/1200ms → **800/400ms**，reap 看门狗 1000→250ms | ≈6.25B/s（0.05%） |
| 不闪黑 | 瞬时写失败 | 不再立刻发黑帧（只有确认断开或 5s 内重复失败才黑） | 无 |

掉线判定最坏时间从 ~2.2s 降到 **~0.65s**；双发只是概率性提升（两份可能同时坏）。
真正要做到"每帧可校验、丢了必补"，需要改固件，最小改动：

1. 0x01 payload 追加 `seq(1B) + crc16(2B)`（26→29B，2.52ms 仍 < 4.17ms 周期）；
2. 设备每帧回 `0x81 seq status`（3B）；主机滑动窗口补发缺 ACK 的 seq（ACK 带宽约 6.25%）；
3. 可选：0x00 回包追加 `lostFrames` 计数，主机据此判断劣化而不用逐帧 ACK。

更彻底的是设备端时基插值（帧带 hold/duration，主机 60~120fps 发关键帧让设备补间），
带宽可降 2~4×——那已不属于最小改动。

## 1.5 灯光 ↔ 通知的对应关系

灯反映的是**聚合后的工作状态**（一个会话一个判定，多会话取最"需要你看"的那个），
不是"每来一条通知闪一下"。具体对应：

| 灯 | 语义 | 由什么触发 |
| --- | --- | --- |
| **白色流转** | 运行中 | agent 在跑；子代理在跑；后台任务 `running/stopping`；inbox 里压着待处理输入（会被再调起）；目标 `active` 但暂时没有 agent 在跑（round-driver 会再调起） |
| **琥珀呼吸** | 等待你 | 模型在问你 / 悬置审批 / —— | `userQuestions` 投影里有 `active` 项（模型在问你）；悬置的审批（权限请求）；目标 `blocked` |
| **绿色常亮** | 已完成 | 回合结束且**没有**未结算工作；目标 `complete` |
| **闪烁红 / 常亮红** | 异常 | 后台任务 `failed` / `killed`；**审批被自动拒绝**（`denied`）；持久化失败。**只在"还没被看到"时闪**，人回来（重新聚焦）或点过确认后转**常亮红**，10 分钟保鲜期内一直亮 |
| **熄灭** | 无信息/关闭 | 开关关闭；没有活跃会话；完成后 2s（已看过的画面会淡出） |
| **彩虹→结果色** | 上电自检 | 每次握手成功（`AI Status Lights OK`）跑一次：1.33s 彩虹 → 0.67s 结果色（绿=就绪 / 黄=降级 / 红=异常） |

### 动画的"按需"原则

所有会动的画面都只在**需要你注意**的时候动：

| 状态 | 什么时候动 | 什么时候不动 |
| --- | --- | --- |
| 异常（红） | 提醒闩挂着（你可能没看到） | 你回来/确认后 → **常亮红** |
| 完成（绿） | 提醒闩挂着 → 缓慢双闪 | 看过之后 → **常亮绿**，2s 后熄灯 |
| 等待（琥珀） | 一直都在呼吸（"模型在等你"本身就是信息） | 已看过 → 停止脉动，亮度不变 |
| 运行（白） | 一直流转（表示还在干活） | — |

亮度全程只由「亮度（%）」配置决定，**不存在自动变暗**。

对应的**通知类型**（`config.types` 里的那 11 个预设）：

| 通知 kind | 参与点灯 |
| --- | --- |
| `task`（任务完成） | ✔ 完成 → 绿；回合结束仍有未结算工作则保持白 |
| `jobs`（后台任务结束） | ✔ `failed`/`killed` → 红；正常结算 → 完成判定的依据 |
| `subagent`（子代理结束） | ✔ 子代理还在跑 → 保持白（"一轮结束 ≠ 会话完成"） |
| `ask`（等待你的输入） | ✔ 黄（等你） |
| `denied`（操作被自动拒绝） | ✔ 红 |
| `goal`（目标完成/阻塞） | ✔ 完成 → 绿；`blocked` → 黄；`active` → 白 |
| `team` / `schedule` / `compaction` | ✔ 参与"是否还在跑"的判定（这些任务未结算时保持白） |
| `startup`（启动播报） | ✘ 不点灯（那是插件自身的播报） |
| `permission`（浏览器通知权限变化） | ✘ 不点灯 |

蜂鸣器只在**跳变**时响：完成（520→660 上行两声）/ 等待（400 单声）/ 异常（260 两声），
冷却 1.5s（多会话接连结算不会连珠炮）。

## 2. 主机端渲染（`src/led-render.ts`）

输入：语义画面（状态 + 标志 + 亮度）+ 时刻；输出：7 颗 RGB。

| 语义状态 | 颜色 | 动画 |
| --- | --- | --- |
| `running` 运行中 | 冷白 `#C8D2E0` | 彗星来回跑（头亮尾暗） |
| `waiting` 等你 | 琥珀 `#FFA000` | 呼吸 |
| `done` 完成 | 绿 `#00C853` | 轻呼吸；已看过（MUTED）常亮暗绿 |
| `error` 异常 | 红 `#FF1744` | 2Hz 硬闪 |
| `off` 熄灭 | 全黑 | — |

- **亮度**：`0..255` 主机端乘到每个通道（固件没有亮度命令）。
- **提醒（ATTENTION）**：自上次聚焦未回来 → 叠一个"亮 110ms / 灭 110ms / 再亮 110ms"的
  周期双闪包络，**不会随时间自己安静**。
- **夜间（NIGHT）**：整体再暗一档。

带宽：26 B/帧 × 240fps ≈ **6240 B/s**（115200 的 54.2%；每帧线上 2.257ms，线速上限 443fps）。

### 帧率与背压

数字的**唯一真相**在 `src/led-timing.ts`（`LED_TARGET_FPS` / `LED_FRAME_MS` / `wireTimeMs`），
别处只准引用、不准再写一套。这一节解释为什么"标 240Hz"曾经是假的、现在又靠什么成立。

| 项 | 值 | 说明 |
| --- | --- | --- |
| 目标帧率 | 240fps | 帧周期 4.1667ms |
| 一帧线上时间 | 2.257ms | 26B × 10bit / 115200（8-N-1） |
| 串口占用 | 54.2% | 余量约 46%；线速上限 ≈443fps |
| 写入下限 | ≈2.60ms | 线上时间 × 1.15，**必须小于帧周期** |

1. **帧循环**：单调时钟（`performance.now()`，不用 `Date.now()` 的 1ms 量化，也不吃系统校时）
   + 一次性定时器链做漂移补偿。回调迟到 **≥1 帧**时**丢掉欠下的帧、从当前时刻重新对齐**，
   绝不 0 延迟补跑 —— 画面按绝对时刻渲染，补跑旧帧只会白烧 CPU、还会瞬间灌满串口队列
   （观感就是"卡一下然后猛跳"）。
   **按需运行**：只在需要连续动画时（running/waiting/error、渐变窗口、自检、握手/重连）用
   4.1667ms；off / 已看过的 done 降到 **250ms/帧**（心跳、探测、重试都保留）。
   帧调度**只用进程级 `setTimeout`**，绝不用宿主的 `ctx.timeout` —— 后者每次调用都会注册
   一个 cordis effect；240fps 下等于每秒 240 棵对象树（崩溃前的 heap snapshot 里确实留下了
   约 318k 个 Timeout + 约 320k 个 Error，与帧数吻合）。这是"灯把宿主堆撑爆"的直接修复点。
   状态里 `frames.idle` / `fps` 会如实反映空闲节拍，别把 ~4fps 误读成掉帧。
2. **有界发送队列**：主线程的 `write()` 只是把帧交给 worker（Windows）或内核缓冲（POSIX），
   "已入队"≠"已上灯"。两个平台共用同一套队列语义（`src/serial-tx.ts`，纯逻辑、有单测）：
   - 队列有界（4 帧 ≈ 104 字节）：够吸收抖动，又不会被灌爆；
   - **动画帧最新优先**：新帧进来时，尚未开始发送的旧动画帧直接作废（画面本来按时刻渲染，
     补发旧帧只会让灯"越走越晚"）；丢弃时返回 `WRITE_DROPPED` 并记进 `link.status().dropped`，
     **不是故障**、不触发重连；
   - **控制帧必达**：握手 / 蜂鸣 / 熄灯 / 自检覆盖严格 FIFO、不插队、不丢弃；队列满时先挤掉
     一个"还没开始发的动画帧"腾位置，挤不出来才判 `full`（由链路走重连）；
   - **短写不截断**：余量留在队首继续写；已经写出过一部分的帧**永不丢弃**（半帧固件必然整帧丢弃）；
   - Windows 侧同一个时刻只允许 1 帧在飞（`MAX_INFLIGHT_WRITES`），POSIX 侧由队列本身限流。
3. **统一的入口**（外部 API 也不例外）：内部动画帧与外部
   `ctx.get('desktopNotify').led.pixels()` 都按"颜色帧 = 可丢、最新优先"处理
   （`rawFrame` 按 MODE 判定），所以**高频调用像素 API 绕不过背压**；
   验证 / 蜂鸣帧仍走必达通道。API 返回里的 `queued` 只表示"真的写进串口了"，
   被背压丢弃时为 `false`（下一次会推最新画面），**不等于**设备已确认显示。
4. **POSIX 兜底**：`O_NONBLOCK` 下 `writeSync` 可能短写或 EAGAIN —— 旧实现把半帧当成功，
   固件校验错后整帧丢弃；同步熄灯帧过去还会**绕过队列插队**（黑帧可能先被接受、旧帧余量再被
   close 追发）。现在同步写也排队、按 FIFO 排空。队列上限 4 帧。
5. **实测口径**（`node scripts/led-fps-probe.mjs`，真实定时器 + 串行化写入模型）：

   | 场景 | 时长 | 渲染 | 交给串口 | 欠帧 | 队列峰值 | 背压丢帧 | 间隔 P50/P95/P99/max |
   | --- | --- | --- | --- | --- | --- | --- | --- |
   | 240fps | 180s | **240.08fps** | 238.2fps（42863 帧 / 1.11 MB） | 6 | 2 | 13（0.03%） | 4.11 / 5.15 / 6.18 / 28.91ms |
   | 240fps + 主线程卡顿（272 次 / 2.0s） | 60s | 239.0fps | 229.9fps | 118 | 2 | 45 | 4.11 / 5.62 / 10.26 / 19.75ms |
   | 125fps（旧默认值，对照） | 8s | 125.0fps | 125fps | 0 | 2 | 0 | 8.15 / 9.17 / 9.69 / 15.75ms |

   读法：`240fps` 是**调度目标**不是"已证明的灯板输出频率"；「交给串口」才是实际写出的帧，
   与目标的差 = 去重（画面没变的那几帧）+ 背压丢弃。P95/P99 的尾巴来自 Windows ~1ms 定时器
   分辨率与事件循环抖动；因为画面按绝对时刻渲染，抖动只影响采样密度，不改变运动速度。

6. **测量边界**：固件的握手回包只证明"设备身份 + 链路活着"，**不能逐帧确认颜色已应用**。
   要证明板子端真的稳定收到 240fps，需要逻辑分析仪量 USART 波形；要程序内逐帧确认，
   得给固件加帧序号 + 回执（那是另一套协议）。Windows 侧还有 ~1ms 的定时器分辨率与
   USB 转串口驱动的批处理，P95/P99 间隔（实测 5.3/7.1ms）就来自这些，不影响"画面按时刻渲染"。
7. **熄灯/退出那一帧走同步写**：异步写只保证"交给 worker"；进程退出或 worker 被 terminate
   时那一帧可能还没发出去，而 WS2812B **锁存最后一帧** → "DSH 关了，灯还亮着"。所以
   `flush()` 优先调句柄的 `writeSync()`：
   - Windows：worker 用 `Atomics.store(syncBuf, n)` + `Atomics.notify` 回报，主线程
     `Atomics.wait` 等结果 —— **不需要事件循环**，所以进程退出路径也等得到；
     `close()` 的 terminate 宽限按在飞帧数放宽（150ms + 250ms/帧，上限 2s）。
   - POSIX：同步写**也排在同一条 FIFO 队列上**（不插队），按 deadline 排空；只有整个队列
     排空才返回成功——所以熄灯帧不会先于旧帧被接受，close 也不会把旧帧余量追发到黑帧之后。
   - 语义仍是"字节已被驱动接受"，**不是** WS2812 已刷新（协议没有逐帧回执）：
     要绝对保证只能扩展固件协议或上逻辑分析仪，这里只承诺"尽力且可验证地交出去"。
8. **异步故障进链路**：worker 卡死 / 串口线程退出通过 `onFault` 立刻变成链路故障
   （关句柄 + 退避重连），并校验代次 —— 旧 worker 的迟到故障不会关掉新连接。
   没有这一步，这类故障只能等"下一次写返回 0"才被发现，画面静止时会拖很久（灯像卡住）。
9. **打开操作的所有权**：`tryOpen()` 领取令牌 `openToken`，并在 `await list()` / `await open()`
   之后都校验代次；**异常路径同样校验** —— 打开超时后旧一轮的失败不会再 `fail()` 打掉新一轮，
   它的 `finally` 也无权清掉新一轮的 `opening` 互斥（否则第三轮会并发 CreateFile 同一个端口）。
   过期的句柄**当场关掉**、绝不安装。
10. **串口线程的读取泵**（`src/serial-worker.ts` + `src/serial-pump.ts`）：所有 koffi 调用都在
    worker 线程，主线程只排队。读缓冲（256B）、"已读字节数"、"已写字节数"全部**模块级预分配复用**；
   读取节奏自适应 —— 打开端口后 / 写出一帧验证帧（MODE 0x00）后 **2ms** 快轮询 2s，
   其余时间 **30ms**（实测把 180 万次/小时的 syscall 降到约 12 万次/小时，空转零分配）。
   收到任意数据立即降速（回包已开始到，不需要继续密读）；读失败只报一次并停泵，交给链路重连。

### 长期方向（本轮不做）

若要求"系统负载波动下依然极平滑"，最彻底的架构是**让 MCU 自己跑动画定时器**、主机只发
状态或动画参数 —— 动画节拍就不再依赖 Windows 事件循环与 USB 调度。这需要扩展固件协议，
不作为本版前置条件。

## 3. 蜂鸣器

| 场景 | 声音 |
| --- | --- |
| 完成 | 520Hz → 660Hz 上行两声（170ms 间隔，音量 16/18） |
| 等待你 | 400Hz 单声（音量 14） |
| 异常 | 260Hz 低沉两声（音量 20/16，间隔 260ms） |

挑音原则：**别刺耳但要听得见** —— 频率压在 260~880Hz（无源蜂鸣器 1kHz 以上就偏尖），
音量 14~20（固件音量 0~100，实测 45 已经太刺耳）。设置页有「启用状态指示蜂鸣器」开关（`ledBuzzer`）。

## 4. 对外 API（`ctx.get('desktopNotify').led`）

```js
const led = ctx.get('desktopNotify').led
if (!led) return                    // 本平台没有串口实现 / 功能未启用
led.scene('done')                    // 语义状态（主机渲染）
led.scene('warn')                    // 黄色警告（1.1.0 新增；只亮 1 秒，优先级 红 > 黄 > 橙）
led.beep({ freqHz: 880, volume: 45, durationMs: 110 })
led.pixels([{ r: 255, g: 0, b: 0 }, ...])   // 必须 7 颗
led.frame(0x00)                      // 白名单原始帧（0x00/0x01/0x02）
led.acknowledge()                    // 解除提醒
led.status()                         // 链路 + 判定 + 设备
```

版本与能力：

- `LED_API_VERSION = '1.1.0-led.3'`（串口控制协议的特殊版本，与通知 API 分开标注）
- `capabilities`：`led.protocol.aisl` / `led.pixels` / `led.scene` / `led.scene.warn` /
  `led.brightness` / `led.beep` / `led.frame` / `led.ack` / `led.preview` / `led.status` /
  `led.host-only`
- 语义状态：`off` / `running`（白）/ `waiting`（橙）/ `done`（绿）/ `warn`（黄，1s 瞬态）/ `error`（红）；
  旧状态名与行为不变（**兼容 1.0.x 调用方**）；`led.host-only` 表示外部推送默认不点灯，
  只有宿主事件或显式 `led.scene()` 才驱动灯。
- 结果对象：`{ ok, queued, reason, protocolVersion }`
  - `ok` = 请求本身合法；`queued` = 真的写进串口队列了（**不等于**设备已确认显示）；
  - 颜色帧（`pixels()`）走"可丢、最新优先"的通道：串口积压时 `queued=false`，
    下一次推帧会用最新画面，不会把旧画面补发出去；验证/蜂鸣帧必定入队（`queued=true`）；
  - `reason`：`''` / `invalid-payload` / `led-disabled` / `link-down` / `unsupported-frame`

## 5. 诊断端点

`POST /dnotify/led`（需要进程令牌**或** DSH 页面的 `admit()` 放行 —— 设置页走后者）：

| op | 作用 |
| --- | --- |
| `status`（默认） | 链路状态、握手结果、当前画面、逐会话判定、`devicePresent`/`ports` |
| `ack` | 解除提醒闩 |
| `preview` | `{ state, brightness? }` 手动点灯（压过判定 5 秒） |
| `beep` | `{ freqHz?, volume?, durationMs? }` |
| `frame` | `{ mode, payload }` 白名单原始帧 |

## 6. 状态词（设置页那行）

只有五个：**未连接 / 未启用 / 运行中 / 异常 / 启动中**。

| 词 | 条件 |
| --- | --- |
| 未连接 | 本机**没有串口设备**（每 15s 枚举一次，只枚举不打开；功能关着也扫） |
| 未启用 | 有设备，但「启用任务状态指示灯」关着 |
| 运行中 | 链路已连上（握手通过） |
| 异常 | 打不开/写不进/握手超时/端点不可达/平台不支持 |
| 启动中 | 正在打开、正在握手，或首屏还没拿到状态 |

**未连接时禁止启用**：开关显示为关且不可点；宿主侧也不驱动、不尝试打开串口。
但**不写回配置** —— 你的设置值原样保留，插上灯就按它生效。

## 7. 常见问题

- **Windows 上设备管理器里是 `USB Serial` 带感叹号、没有 COM 口** → CH340 驱动没装，
  装 WCH 驱动后会出现 `COMx`；在此之前插件只能显示「未连接」。
- **有 COM 口但显示「异常」** → 该口被别的程序占用，或插的不是这块板子（握手超时）。
- **灯不亮但状态是「运行中」** → 固件版本太老（不支持 0x01）或灯珠线序不对。
